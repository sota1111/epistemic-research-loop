# インシデント記録:10列制約の無承認継承(2026-08-29〜2026-08-30)

**分類:** 設計上の重大な見落とし。[v043 ps -ef 盲検リーク事例](v043_blindness_incident_ps_ef_leak.md)
と同じ形式で記録する——技術的な漏洩ではなく、**ユーザーの承認を得ずに全 real-data 実験の
射程を狭めていた設計上の欠陥**。

## 何が起きたか

v0.3.7 の**合成データ**生成器(Track A)は `CANONICAL_FEATURES` という 11 スロット
(実特徴10+派生1)の固定スキーマを持っていた(2026-08-27 作成、commit `d3c74992`)。
2026-08-29、Track B(v0.4.1、IEEE-CIS への real-data 適用、commit `8fbca42`)を構築する際、
この合成データ用スキーマを**無改変のまま**実データに適用した——コミットメッセージ自身が
「reusing v0.3.7's ... schema ... unchanged」と明記している。

`docs/v041_track_b_preregistration.json`(開封前に凍結された設計文書)には
「4パック×10列に分割する」という設計が記載されていたが、その理由として書かれていたのは
`canonical_slot_reuse: "既存の _agent_rows/_visible_column_map/packet-writing コードを
無改変で再利用できるから"` という**実装上の都合**であり、実コンペでの発見能力にとって
何列が必要かという検討ではなかった。さらに、同文書の「開封前に開示するリスク」セクション
(model memorization・単一データセットの汎化限界・小さい陽性数等を列挙)には、**この
10列制約そのものは一切含まれていなかった**——リスクとして意識的に検討された形跡がない。

この制約は v0.4.2(Santander への一般化)・v0.4.3(全ラウンド)を通じて無改変のまま
継承され、本セッションだけで 90 run 以上の実エージェント実行がこの制約下で行われた。

## なぜ問題か

ユーザーへの承認確認なしに、「エージェントに実コンペの何%の情報を見せるか」という、
発見できる構造の上限を直接左右する設計選択が行われた。2026-08-30 の v0.4.4 pilot
(全106列、後述)は、列数を増やすだけで capacity-matched baseline の transfer AUC が
0.774(参考値)まで伸び、実エージェントの最終スコアはさらに 0.8315 に達することを
示した——10列制約が、単なる些末な実装詳細ではなく、**発見できる構造の質・量を
直接制限していた**ことが実証された。

## 影響範囲の切り分け

**やり直し不要(内部妥当性は列数と無関係):**
- Track A(合成データ、v0.3.x〜v0.4.0)——実コンペと無関係
- Matched Negative 構築(`_destroy_target_structure`)・FSPR 検証・identifiability
  preflight の設計・修正——列数に依存しないロジック上の正しさの問題
- 盲検監査の手法・[ps -ef 盲検リーク事例](v043_blindness_incident_ps_ef_leak.md)の
  発見と修正——列数と無関係な、プロセス可視性の話
- 「単一 seed の novel-structure 発見は信頼できない」等の方法論的教訓——実験の進め方
  そのものについての学びであり、列数に依存しない
- v0.4.4 pilot(全106列設計)——本インシデントを受けて既に正しい設計で構築済み

**再解釈が必要(再実行は不要、記述の訂正のみ):**
- IEEE-CIS の layer1(上位解法技術クラス)一致率が全ラウンドで 0% だったという事実
  そのものは変わらないが、**「匿名化の効果」とだけ説明していた既存ドキュメントの解釈は
  不完全だった**——実際には「匿名化」と「10列という深刻な列数不足」の両方が効いており、
  v0.4.4 pilot の結果は後者が主要因である可能性を示唆する。

**やり直しが必要:**
- **v0.4.3-f(sol reasoning-effort 多様性ラウンド、4ラウンド・34 run)。** 「解法の
  多様性・上位解法相当の存在・未知構造発見」という3つの価値基準を検証する目的で
  行った本体の実験が、10列制約下で行われていた。この実験が導いた結論(diversity 指数・
  layer1/layer2 一致率・「加法性の限界」候補の観測など)は、**「10列という上限の中での
  話」でしかない**——全特徴量を見せた場合にどうなるかは未検証のまま。

## 対応

1. 本インシデントを記録(このドキュメント)。
2. v0.4.4 pilot(既に完了)で、全特徴量 + ローカル疑似採点ループという修正済み設計が
   機構として機能することを確認済み。
3. 既存の v0.4.3-f 関連ドキュメント([IEEE-CIS側](v043_sol_effort_diversity_ieee_cis.md)・
   [Santander側](v043_sol_effort_diversity_santander.md)・
   [クロスコンペ統合分析](v042_cross_competition_synthesis.md))に、本インシデントへの
   参照と「10列制約下での結果である」という注記を追加した。
4. 今後の計画は [c_lite_v044_policy.md](../c_lite_v044_policy.md) に記載——v0.4.3-f の
   sol reasoning-effort 多様性ラウンドを、全特徴量設計で同じ段階的厳密さ(screening→
   確認→population拡大)でやり直す。
5. **新しい不変条件として明文化:** 既存コードの無改変での流用が、後から見て「発見の
   上限を左右する」ような性質を持つ場合、それが自明な実装詳細に見えても、preregistration
   文書の「開示するリスク」節に明記し、可能な限りユーザーに一言確認を取ること
   ([c_lite_v044_policy.md](../c_lite_v044_policy.md) 不変条件参照)。
