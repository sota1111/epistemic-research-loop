# v0.4.4 全特徴量 + 疑似採点ループ pilot — 事前登録

**作成日:** 2026-08-30
**status(2026-08-30、pilot完了):** 1エージェント・1回の実行(`v044-pilot-a01`)で
機構の実現可能性を確認し、3目標全て達成——結果は
[v044_full_feature_pilot_results.md](v044_full_feature_pilot_results.md)を参照。

**背景:** ユーザーからの指摘(該当ターン参照)により、既存 v0.4.1〜v0.4.3 の Track B/
multi-competition pipeline が `CANONICAL_FEATURES`(固定10スロット)という、元々は
**合成 Track A** 用に選ばれた小さな数に由来する制約を real データにも無検討で継承して
いたことが判明した。この10列制約は IEEE-CIS の layer1(上位解法技術クラス)一致率が
全ラウンドで 0% だった直接の機械的原因である(UID復元等の上位解法技術は複数の特定の
列を同時に見て初めて到達できるが、ランダムな10列抽出ではその組み合わせに到達しにくい)。
本 pilot は、列数制約を外した別トラックとして、(a) 全(匿名化)特徴量を見せる、
(b) 実際の Kaggle 提出の代わりに、ローカルな疑似採点ツールで confirmation 領域への
提出→採点を繰り返せるようにする、という2点を検証する。

## 1. 何を検証するか(このラウンドのスコープ)

**検証する:** 1エージェント・1回の実行で、以下が機構として機能するか:
1. 全(匿名化)特徴量を含むデータをエージェントに渡せるか。
2. エージェントが confirmation 領域への予測をローカルツール経由で繰り返し提出し、
   都度スコア(AUC)を受け取れるか(何回呼び出すか、スコアがどう推移するか)。
3. transfer 領域(封印)への最終提出を Controller 側で独立採点できるか。
4. 上記の過程で盲検原則(データセット識別・解法情報の非開示)が破られないか。

**検証しない(次段階に持ち越す):** 複数 seed での再現性・taxonomy 照合・複数
competition 横断比較・本格的な P2 判定枠組みとの統合。これらは pilot が機構として
機能することを確認した後、別途 preregister する。

## 2. データ設計

- 対象コンペ:IEEE-CIS(layer1 一致率 0% という既存結果があり、列制約緩和の効果が
  最も検証しやすいため)。
- 列選択:`select_generic_feature_groups` と同じ一般的フィルタ(数値dtype・
  missingness閾値0.02)を適用するが、**disjoint な10列グループへの分割は行わず、
  条件を満たす列を全て**渡す(実測:106列、既存の10列から10倍以上)。列名は既存と
  同様ハッシュ化する——blindness原則は列**数**ではなく列**意味論の秘匿**にあり、
  106列でも同じ原則で満たせる。
- 行分割:research(ラベル付き、5,000行)・confirmation(ラベル秘匿だが疑似採点
  ツールで繰り返し照会可能、1,500行)・transfer(ラベル完全封印、Controller側で
  最終採点、1,500行)——既存 pipeline の3領域構造をそのまま流用(意味も類似:
  research=学習、confirmation=Kaggle の public LB 相当、transfer=private LB 相当)。
- row_id は既存と同様 opaque ハッシュ ID。

## 3. 疑似採点ツールの設計(ネットワーク不使用の原則との整合性)

- `scripts/v044_score_confirmation.py` という**ローカルスクリプト**として実装する
  (常駐サーバーやネットワーク通信は使わない)。エージェントは
  `python3 <固定パス> --submission <自分のpredictions.csvパス>` という形でサブ
  プロセスとして呼び出す——これは「ネットワークを使わない」という既存の不変条件と
  矛盾しない、ローカルなツール呼び出しである。
- confirmation 領域の正解ラベルは Fernet 暗号化して、エージェントの作業ディレクトリ
  **外**(`.controller_truth/v044/`)に保存し、復号鍵も同様にエージェント作業
  ディレクトリ外(`.state/v044/`)に置く。エージェントには「このディレクトリ外を
  探索しない」という既存の RUNNER.md 指示をそのまま適用する。
- **既知の限界:** この環境の codex sandbox(`danger-full-access`)は OS レベルの
  真の分離を提供しない(`ps -ef` 盲検リーク事例で確認済み)——したがって、この
  ツールも「指示 + 事後監査」による blindness であり、暗号学的に破られない保証では
  ない。既存の全ての盲検制御と同じ前提に立つ。
- 呼び出し回数の上限を設ける(20回)——プロービング攻撃的な悪用を防ぐ安全策であり、
  今回のような指示に従う研究エージェントには通常発動しない想定。
- 各呼び出しは Controller 側のログファイル(エージェントの作業ディレクトリ外)に
  記録し、事後分析で「何回呼んだか」「スコアがどう推移したか」を確認できるようにする。

## 4. エージェント向け契約(既存の v037 epistemic cycle 契約は流用しない)

本 pilot は「機構が動くか」の確認が目的であり、既存の cycle/lineage/null-provenance
という重い epistemic 契約(v037_agent.py)を流用すると、機構検証と手続き遵守の
2つの問題が混ざってしまう。そのため、pilot 専用の**最小限の契約**を新設する:
`version`・`suite_id`・`run_id`・`approach_summary`(自由記述、後の分析用)・
`confirmation_calls_made`(自己申告、Controller側ログと突合)・
`transfer_predictions`(最終提出、row_id整列)。本格スタディへ格上げする際に、
必要であれば v037 epistemic 契約と統合する。

## 5. 実行構成

sol(codex/gpt-5.6-sol)のみ・reasoning_effort=high(v0.4.3-fで最も頑健と確認された
水準)・1 run のみ。

## 6. 実行順序

1. 本ドキュメントで preregister(完了)
2. データ準備・暗号化ラベル・ツール実装
3. 単体テスト(合成データでの plumbing テスト)
4. build-only preflight(実 IEEE-CIS データ、agent実行なし)
5. 盲検監査(ツール自体・エージェントview)
6. **1 run のみ実行**、`ps -ef` リーク事例の教訓を踏まえ、起動コマンドの引数に
   コンペ名を含めない
7. 事後監査:(a) confirmation call log の呼び出し回数・スコア推移、(b) transcript
   に暗号化ラベル・鍵・コンペ識別子が一切現れていないことを確認、(c) transfer 領域の
   最終スコアを Controller 側で独立算出
8. 結果を文書化し、機構が機能したかどうかをユーザーに報告。機能していれば、本格
   スタディ(複数seed・taxonomy照合・Santander横展開)を改めて preregister する。
