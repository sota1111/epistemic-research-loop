**新設:** 2026-09-06。[ERL を完成させるための引き継ぎ書](../v050_course_correction.md) §3 の 10。
**登録簿:** [layer2_registry.json](layer2_registry.json) / 判定 `src/epistemic_loop/taxonomy/layer2.py` /
表示 `erlctl taxonomy status`

## 0. なぜ別ファイルなのか

[表形式コンペ横断メタ技術 taxonomy](tabular_technique_taxonomy_layer2.md) が集めているのは
**解法の技術**である。本ファイルが集めるのは**測る装置についての知見**であり、
別の物である。

区別が実務上効くのは、**出題非依存性の根拠が違う**からである。
解法技術が問題クラスを跨ぐかは、その都度の証拠がないと言えない。
一方、装置クラスは **「ローカルに作った採点系」と「本当の採点系」の関係についての知見**で、
その関係はコンペが何であっても存在する。だから**実際に問題クラスを跨いで再発した。**

**そして本ファイルの 2 クラスは、実際に跨いで観測されている。**
[表形式側](tabular_technique_taxonomy_layer2.md) の 3 クラスは 1 つも跨げていない。

## 1. 昇格した装置クラス

昇格条件は解法側と同一(問題クラス 2 以上・コンペ 2 以上・エージェントモデル 2 以上)。
判定はコードが当てる。**下の状態は手で書いた主張ではなく、登録簿からの導出である。**

### A1. ローカル指標が、結果を決める量とは別の量を測っている 【昇格・3 問題クラス】

ローカルの採点系は必ず自作であり、**自作した瞬間に「本当の量」との差が入る。**
差が小さいことは仮定であって観測ではない。

| 問題クラス | コンペ | 観測 |
| --- | --- | --- |
| 表形式予測 | IEEE-CIS | ローカルの数字と hidden endpoint の**相関逆転** |
| アルゴリズム提出 | SIGNATE NEDO | 配布 evaluator が接地荷物を充填率から落とす / **自作の揺動試験が恒常 0 を返したまま 4 指標で順位付けしていた** |
| エージェント対戦 | kaggriculture | 公開上位のリプレイで組んだ league が**実 LB の順序を反転**/ 8 月のレーティングを 9 月の分布へ載せた |

**検出法:** ローカル指標と実スコアの**順位相関を必ず測る。**
値の一致ではなく**順序の一致**を見る。指標が定数を返していないかを毎ラウンド確認する
(NEDO の 2 件目は「分散 0 の指標」で、平均だけ見ていると気づけない)。

### A2. ローカルは差を誇張する(local→real の傾き < 1) 【昇格・2 問題クラス】

| 問題クラス | コンペ | 観測 |
| --- | --- | --- |
| アルゴリズム提出 | SIGNATE NEDO | 実 public ≈ **0.589** × ローカル + 28.18(n=9、RMSE 3.39) |
| 表形式予測 | IEEE-CIS / Santander | 同じ向き(傾き < 1) |

**A1 とは別のクラスである。**A1 は「測っている量が違う」、A2 は
「**測っている量は同じでも、縮尺が違う**」。A1 が無くても A2 は起きる。

**検出法:** ローカル差をそのまま期待利得に使わない。**傾きを当てはめて縮めてから**
選定・停止に入れる。傾きは提出のたびに再当てはめする。
`measurement/task_scores.py` の生ベクトル保存があれば、傾きを変えても再採点は要らない。

## 2. 候補(未昇格)

### A3. 課題セットが張っていない軸は、装置の盲点になる 【候補・1 問題クラス】

エージェントの弱点に見えるものが、**課題セットがその軸を張っていないだけ**であることがある。
張っていない軸の失敗は、**装置には原理的に見えない。**

| 問題クラス | コンペ | 観測 | 強度 |
| --- | --- | --- | --- |
| アルゴリズム提出 | SIGNATE NEDO | 課題ジェネレータが要件(5)を一度も生成せず、index/位置の取り違えを**原理的に検出できなかった**(ローカル 12/12・composite 66.05 に対し**実スコア 0**) | 直接 |
| アルゴリズム提出 | SIGNATE NEDO | プローブが積載率 43.5〜55.2% しか張らず、候補のいる 59〜66% へ外挿できなかった / エージェント課題セットが順位付け課題セットより **+1.71** 高かった | 直接 |
| 表形式予測 | IEEE-CIS | 単一 suite instance の false promotion が独立に 4 回 | **arguable** |

**昇格していない理由:** 直接観測が **1 問題クラス(アルゴリズム提出)に閉じている。**
表形式側の 1 件は「suite instance が 1 つだけ違う挙動をした」であって、
「課題セットが軸を張っていない」とは**同じ主張ではない。**登録簿では `arguable` として
記録し、**昇格には数えていない。**

> 引き継ぎ書 §3 の 10 は 3 クラスすべてを「2 問題クラスで独立観測済み」としていた。
> **機械的に当てると、A3 はそこに届いていない。**A3 を昇格させたいなら、
> 表形式側で「課題セットが張っていない軸」の直接例を挙げるか、
> **1 問題クラスの知見として扱うかのどちらかである。**
> 規則を緩めて通すことはしない(それが §2.5 で撤回した誤りである)。

## 3. 使い方

- 新規コンペの taxonomy は preregister 時点から**層1(コンペ固有)・層2解法・層2装置**の
  3 参照を持つ形で作る
- **装置クラスはラウンド 0 で当てる。**A1・A2 は「回してから気づく」ものではなく、
  **最初の提出が返ってきた時点で測れる。**A3 は課題セットを設計する時点で効く
- **Controller 専有。**プロンプト・契約・エージェント可視のファイルに複製しない。
  装置の盲点を測られる側に渡したら、それは測定ではなくなる
